# EVE-43 Keycloak 26.8.2 vulnerability register

Image `quay.io/keycloak/keycloak@sha256:c68e286cacd87b942ac1939a0a1481461109d6acd3a57dc496969a319a76bbf0` (amd64 `sha256:4da21f9a53bcbac1026a0d654b740a81e98e5de4c45457076acc74b4d94b1551`, arm64 `sha256:923a431c08971d49727a857e64870d8d63b5bf294a730e5dde729b5138c26c9e`). Scanned on 2026-11-18 with Trivy 0.76.2 (release checksum verified), vulnerability database updated 2026-11-18T07:15:21Z. Both architectures report the same 60 occurrences: 6 high, 27 medium and 27 low. This scan supersedes the 2026-11-17 Quay register for current counts; that register's exact-byte analysis of Guava, MariaDB and sed still applies.

Runtime observations come from the pinned image started on loopback with the synthetic realm. `/proc/1/maps` mapped `libnss3.so` but neither `libsoftokn3` nor SQLite. The open jar list included Guava 33.6.0 and OpenTelemetry 1.62.0 but no MariaDB driver. That run used the development H2 database; production must set `KC_DB=postgres`.

Jonathan approved adopting this component on 2026-11-18 ([decision](../planning/decisions.md#later-owner-decisions---2026-11-18)). Residual rows are accepted under that decision with the stated controls; they are not reported as fixed. Re-scan before every deployment and move to the first supplier 26.8.x respin that fixes Guava, MariaDB or OpenTelemetry.
