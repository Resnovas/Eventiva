# Eventiva planning record

This directory is the repository-native index of Eventiva's approved direction, delivery sequence and remaining acceptance work. It mirrors Linear; it does not approve work. Start with the [complete EVE issue index](issues/README.md), [timeline](timeline.md) and [decision index](decisions.md).

## Authority and synchronization

1. Read the owning Linear issue and its latest owner decisions before changing a plan or API. A new binding owner decision on Linear governs until this repository mirror is updated. An agent proposal, an issue marked Done, a passing test or an Amp summary is not a new owner approval.
2. Keep approved direction, proposed choices, implementation present, evidence verified and release authorized separate. Cite the decision's issue/comment and date. If approval provenance is missing, say `unverified` or `proposed`; do not infer approval from code.
3. Update the owning issue and the affected repository Markdown in the same delivery increment. Update the timeline's completed/current/upcoming rows and dependency graph whenever delivery order, status or an acceptance gate changes. Preserve the original scope of broader issues instead of closing them for a narrow checkpoint.
4. Change detailed contracts in their existing home: [modular platform specification](../architecture/modular-platform.md), [platform/marketplace decisions](../architecture/eventiva-platform-and-marketplace.md), or the relevant feature guide. Link them here rather than maintaining a second specification. Preserve unresolved discrepancies until the owner resolves them.
5. Put the exact commit, commands, decisive output, executed target and limitations on Linear. Distinguish evidence rerun on the combined tree from another lane's reported results. A build/export is not a native-device test; a process-local model is not durable recovery or production readiness.
6. Update the people guide and corresponding `ai-docs/src` source. Regenerate `LLMS.md` with `node tools/ai-docs/docgen.mjs`; update the graph with `sh tools/graphify/graphify update` without build output. In coordinated work, reserve paths first and let the coordinator perform shared regeneration, root wiring and delivery once. Do not edit generated files by hand.
7. If Linear or a required source cannot be read, label the mirror stale with the last verified date and exact missing update. Continue safe local work; do not invent issue updates, approvals or current status. Report the synchronization blocker before delivery.

Example: an owner changes a producer's restart identity on EVE-45. Link that decision in [decisions.md](decisions.md), change EVE-45's current/next work in [timeline.md](timeline.md), amend the existing hook guide/agent source through its reserved owner, run the affected checks, and post the commit and evidence to EVE-45/EVE-261. Do not mark platform integration complete just because the journal's focused tests pass.

## Refresh the complete mirror

The offline renderer is `tools/documentation/linear-mirror.mjs`; its owner-authorized normalized input is `tools/documentation/linear-snapshot.json`. It uses Node and no new dependency. Generated regions are delimited by `<!-- linear:generated:start -->` and `<!-- linear:generated:end -->`. Everything outside those markers, especially `Repository context (human-maintained)`, is preserved byte-for-byte. Reserved generation-marker text in source prose is escaped, not interpreted as an overwrite boundary. The snapshot and marked regions are generated; this guide, `decisions.md` and `timeline.md` are human-maintained. Never run a blanket Markdown formatter over generated regions: refresh them with the renderer instead.

### Long-term live sync and workflow

Run `node tools/documentation/sync-linear.mjs` to read the complete current EVE set and refresh the snapshot/pages, or `node tools/documentation/sync-linear.mjs --check-live` to check drift without writing. Set exactly one securely injected `LINEAR_API_KEY` (read-only personal key) or `LINEAR_ACCESS_TOKEN` (OAuth); never pass a token as a command argument or commit it. Missing credentials fail explicitly before acquisition, not a successful empty refresh. The command uses only GraphQL read queries at `https://api.linear.app/graphql`, follows issue/label/comment/relation connections, cross-checks two full issue enumerations, and fails closed on HTTP/API/schema/pagination/credential-shaped input errors. It does not mutate Linear, push Git, open pull requests or change secrets/settings. Read authority is not repository delivery authority. Review the diff, reconcile the planning source inventory and decisions, update human context and commit through the normal repository delivery owner.

The coordinated root command `node --run documentation` runs the fixture suites, offline mirror/planning consistency and trusted-base documentation ratchet. Root `check` includes it; the Nx documentation target is uncached. `.github/workflows/linear-mirror.yml` performs a separate daily/manual read-only drift check using the securely injected `LINEAR_MIRROR_READ_KEY`; unavailable credentials must be reported as unavailable, not synchronized. It does not automatically overwrite or deliver repository context. Live GraphQL acquisition has fixture/schema review but has not been executed with a standalone authenticated credential in this orb; initial acquisition used the connected MCP server. Offline success cannot prove that today's Linear state is unchanged. No credential or shared setting is created by these tools. Official API references: [authentication and endpoint](https://linear.app/developers/graphql), [pagination](https://linear.app/developers/pagination), [schema used to verify fields](https://github.com/linear/linear/blob/073db61faaf87dcd6a457bc539a1ee01b742eba1/packages/sdk/src/schema.graphql).
