## Linear description

## Goal

Crew see their Eventiva shifts in the calendar they already use, with no vendor integration needed.

## Context

* Slice 10 of F2 (<issue id="1c8c53a0-396b-43a7-8fb9-c138dbbc70b2" label="EVE-67" href="https://linear.app/resnovas/issue/EVE-67/f2-scheduling-and-rosters-crew-availability-shifts-offers-call-sheets" /> section 8, decision 6 recommended a). Read-only ICS feeds first; two-way Google and Microsoft sync stays a later slice behind a `CalendarSync` port and needs vendor approval.

## Scope

1. `calendar.feed.issue` returns a secret ICS URL per person with scope (confirmed only, or confirmed plus offered); `calendar.feed.revoke` rotates it.
2. Feed served from the HTTP surface (<issue id="0ab161c4-ed9c-4581-86fe-91fa1f4216aa" label="EVE-46" href="https://linear.app/resnovas/issue/EVE-46/p17-build-the-http-api-streaming-and-the-typed-client-from-the-action" />) with call time, location and a deep link to the shift in the app; no other people's data.
3. Correct timezones (VTIMEZONE) and stable UIDs so updates replace rather than duplicate.
4. Revoked guest access invalidates feeds (<issue id="7f612e80-3332-4acf-a74c-d35db06fe4e8" label="EVE-43" href="https://linear.app/resnovas/issue/EVE-43/p14-build-identity-and-access-orgs-authorization-user-profiles-and" />).
5. `CalendarSync` port interface defined with no adapter.

## Acceptance criteria

* Feed validates against RFC 5545 and imports into a standard calendar client with correct times across a DST change.
* Changing a shift time updates the same event, not a new one.
* A revoked URL returns 404 within one request.

## Constraints

Effect-TS v3; feed token never logged; no vendor and no new dependency without approval here; ships to main with `node --run check` results pasted here.

## Done signal

Merged to main, validator output and check output here.
