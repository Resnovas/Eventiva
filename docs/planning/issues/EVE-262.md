# Eventiva observational extension-hooks platform — executable specification (2026-11-15)

## Intent, decisions and non-goals

A module must extend another existing module's runtime, workflow, execution steps, UI and logging using central registries and stable published contracts, with **no edits to the host or source feature**. User decision: hooks observe and add *separate authorized side effects only*; hooks cannot block, reject, rewrite, replace, intercept mutable state, impersonate original caller, bypass approvals, trigger unauthorized safety actions or alter the transaction outcome. Do not add guard/veto hooks under another name. Existing Baseline, Sensitive, Restricted/Regulated and Vault/Zero-Knowledge security profiles + A1–A5 assurance apply. Registration/manifest signature/trust do not automatically confer decrypt entitlement. The exact archived `Examples/preamp` HookRegistry/onLoad + `Effect.logInfo` + structured annotations Eventiva ASCII word-art is a mandatory reference fixture (verify actual bytes first).

## Public contracts

* A typed, versioned, discoverable HookDefinition: stable namespaced identifier, schema version, publisher/owner, classification, authorized visibility, payload schema, approved redaction/projection, delivery method, ordering guarantees, idempotency, compatibility, retention and event trigger.
* HookSubscription: module/version/generation, tenant and resource scope, minimal capability, optional bounded filtering on permitted fields, endpoint/handler reference, timeout/retries/backoff/dead-letter or explicit best-effort, trace correlation and isolated side-effect identity. Dynamic registration and unregistration must be audited, stateful, reversible and lease-aware.
* Separate internal event production, immutable event projection and external delivery; authenticated issuer from runtime, not supplied untrusted payload. Stable event ID, occurrence time, trace ID, tenant scope, aggregate ID/version and event schema; no secret content by default.
* Typed event families: platform.module.registered/validated/installed/activated/ready/deactivated/unregistered/updated/failed/recovered/retired; execution.created/started/suspended/resumed/completed/failed/cancelled; execution.step.started/completed/failed/retried/skipped/cancelled; resource.created/updated/deleted where authorized. Define whether each event fires before/after commit; no subscriber on transactional critical path. Events describing proposed activity are observations, not permission to interfere.
* Executions retain stable ID and exact workflow and extension generation/version; hook delivery must not require original module source changes. No arbitrary state mutation, direct DB connection or direct webhook outside separately authorized actions.

## Runtime architecture

Trusted execution emits immutable events into a central gateway after authorization. For authoritative operations, use atomic transaction/outbox with immutable event references; async worker projects minimal subscriber-specific payload *after commit*, checks currently valid grants, publishes side effects through permitted action services, retries idempotently and exposes status/dead letter. No arbitrary subscriber executes synchronously inside original transaction, and delivery failure never repeats original execution. Service-level queues have quotas, circuit breakers, bounded backpressure and monitoring; emergency/show control must remain independent and not wait on listeners. Ordering: per aggregate/stream when guaranteed, never falsely claim global order. Registration and removal use kernel scope/lease coordination; disable stops new dispatch, drains or safely cancels queued delivery per documented policy, no duplicate side effects. Runtime update pins active execution to compatible generation and proves no listener leaks.

## Security requirements

Baseline: scoped authorized subscriber minimal fields; Sensitive: purpose- and field-scoped visibility, redaction and audited grant; Restricted/Regulated: explicit owner and policy approval, assured workload, separately filtered event boundary, revocation and detailed audits; Vault/Zero-Knowledge: no ordinary plugin hook or decrypted payload; only specifically authorized policy-governed minimal boundary notification where allowed, otherwise none. Accounting/payment and emergency events must be separated from commands and control systems: never expose credentials, keys, bank data, vault plaintext, protected incident details or actionable show-control commands. Even timestamps/event existence may be classified; deny by default. Permissions checked on enrollment AND at delivery; revoke immediately stops future delivery. Verify tenant isolation, identity, A1–A5 enforcement, workload attestation when required, no leak through errors, traces, UI, retries, dead letters or console.

## Acceptance tests

1. Unmodified workflow publishes execution + per-step events. Separate sample extension subscribes, logs trace-correlated observations and performs one explicitly authorized additive notification. Disable, hot-upgrade, unregister and restart preserve correct behavior without duplicate processing or stale listeners.
2. Recovery after producer crash between committed step and delivery, consumer retry/crash, duplicate event, lag/queue overflow and cancellation: original state remains committed once, side effect idempotent, dead-letter recoverable.
3. Negative tests: attempts to mutate/veto original execution, subscribe without consent, read higher-classified fields, request decryption, bypass tenant scope, issue emergency show-control command, subscribe after revocation, depend on unsafe ordering, and run inside protected execution all fail closed.
4. Event schema/version compatibility and upgrade with active execution pinned. Clear distinctions between process-local proof, durable storage/outbox, multi-runner fencing and web/native proof.
5. Pre-Amp original Eventiva ASCII word-art (exact verified source) on platform.ready through Effect structured logging; one output per successful generation and no core feature edits. Validate console sink; telemetry/span correlation with UI module and step.
6. Effect/vitest focused and failure-injection test evidence, lint/Nx import isolation, docs for developers/agents, security review and replay-safe operational runbook. Publish sample manifest, event contracts, sequence diagrams and explicit incomplete platform targets. Full CI and independent review before owner-authorized integration to main.
