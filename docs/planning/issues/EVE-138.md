## Linear description

## Goal

Crew clock in and out against their shift, even with no signal, and approvers sign off accurate hours that payroll and costing can trust.

## Context

* Slice 9 of F2 (<issue id="1c8c53a0-396b-43a7-8fb9-c138dbbc70b2" label="EVE-67" href="https://linear.app/resnovas/issue/EVE-67/f2-scheduling-and-rosters-crew-availability-shifts-offers-call-sheets" /> sections 4, 5 and 11). Decision 1 (recommended a): F2 owns time capture and approval; F12 consumes approved timesheets; F11 reads hours per event.

## Scope

1. TimeEntry append-only: clock in, break start, break end, clock out, with device time and server time stamped at sync; crew chief can clock on behalf with reason.
2. Optional location stamp at clock events only (flag `f2-geo-clock`, opt-in per org and person, 90-day retention).
3. Timesheet per person per period built from entries, with variance against rostered times; `timesheet.submit`, `timesheet.adjust` (reason, agent confirm), `timesheet.approve` and `timesheet.reject` (approval always), approved is locked.
4. `timesheet.export` produces a versioned batch for F12 and a CSV; exports are idempotent per period.
5. Clock and Timesheet review screens with projections.
6. Payroll contract (agreed with F12, which closed <issue id="e08704c6-b901-4fc2-8753-73aaf09f694f" label="EVE-83" href="https://linear.app/resnovas/issue/EVE-83/f122-build-time-capture-clock-in-and-out-and-time-entries-offline" /> and <issue id="6d951ef7-861e-43b3-aaa8-3f2ba0d53f56" label="EVE-85" href="https://linear.app/resnovas/issue/EVE-85/f123-build-timesheets-draft-from-roster-submit-and-approve" /> as duplicates of this issue): approver scope per Event (and Department where granted); an approval made offline against a timesheet that changed or was locked meanwhile is rejected at sync as stale; export lines carry Event, Phase, Department, engagement type and source refs (assignment, time entry ids) plus rostered and actual times; `timesheet.lock` (called by F12 when a pay run locks a period) makes the covered timesheets immutable, after which `timesheet.adjust` fails with `PeriodLocked`. Allowances (meal, travel, late finish) stay in F12 (<issue id="f734b33a-bc05-42ca-85ac-186863c86523" label="EVE-87" href="https://linear.app/resnovas/issue/EVE-87/f124-build-pay-run-calculation-on-durable-runs" />).

## Acceptance criteria

* Clock in offline at 07:58 device time, reconnect at 10:00: entry keeps 07:58 device time and 10:00 server time; variance shown.
* Editing an approved timesheet fails without `timesheet.adjust`; adjustments appear in audit.
* Export of the same period twice returns the same batch id.
* No location is stored when the flag or consent is off (test).
* An offline approval of a timesheet edited online in the meantime is rejected as stale on sync.
* After `timesheet.lock`, adjust and approve fail with `PeriodLocked`; export lines include every field F12 listed.

## Constraints

Effect-TS v3; personal data rules in <issue id="1c8c53a0-396b-43a7-8fb9-c138dbbc70b2" label="EVE-67" href="https://linear.app/resnovas/issue/EVE-67/f2-scheduling-and-rosters-crew-availability-shifts-offers-call-sheets" /> section 11; behind flag `f2-scheduling`; no new dependency without approval here; ships to main with `node --run check` results pasted here.

Payroll (F12, EVE-61) agrees F2 owns time capture and timesheets. EVE-83 and EVE-85 are closed as duplicates of this issue. Please carry these payroll needs here:

* Clock events are append-only with an idempotency key, device time and server time, so two offline devices never overwrite each other. Flag clock skew over 5 minutes.
* Show the variance between clocked and rostered time per entry, with an org threshold (default 15 minutes).
* An approval queued offline against a timesheet that changed since is rejected on sync and flagged.
* Approver scope is per event or team. A timesheet that spans two events needs each event's approver.
* Clock-in location is an org opt-in, recorded only at clock in and out (F12 decision D5).
* `timesheet.export` lines carry Event, Phase and Department where known, the engagement type, and a source ref per entry, so `payroll.run.explainLine` can trace pay back to the time it came from.
