## Linear description

## Goal

Every person who can be rostered has a crew profile with roles, and states when they can and cannot work, so schedulers and agents can ask "who is free" and get a trustworthy answer.

## Context

* Slice 1 of F2 (parent <issue id="1c8c53a0-396b-43a7-8fb9-c138dbbc70b2" label="EVE-67" href="https://linear.app/resnovas/issue/EVE-67/f2-scheduling-and-rosters-crew-availability-shifts-offers-call-sheets" />, sections 4 and 5). Builds on the generic Resource and availability tables of <issue id="97915f03-fb56-4efc-bb5a-15e8b62b96b2" label="EVE-33" href="https://linear.app/resnovas/issue/EVE-33/port-scheduling-primitives-for-availability-bookings-and-rosters" /> (Resource kind `person`).
* Qualifications are owned by F13 (decision 2 in <issue id="1c8c53a0-396b-43a7-8fb9-c138dbbc70b2" label="EVE-67" href="https://linear.app/resnovas/issue/EVE-67/f2-scheduling-and-rosters-crew-availability-shifts-offers-call-sheets" />, recommended); until F13 exists this slice ships a `QualificationReader` port with an in-memory adapter.
* Leave approved in F13 appears here as an AvailabilityException of kind `unavailable` through the same port.

## Scope

1. Tables CrewProfile and Role through the shared schema package (<issue id="c31b6b08-1532-4a7a-945f-24a70bbab765" label="EVE-23" href="https://linear.app/resnovas/issue/EVE-23/split-core-into-portable-contracts-and-backend-runtime-with-a-shared" />), `org_id` on every row.
2. Actions `crew.profile.get`, `crew.profile.update`, `crew.role.define`, `availability.set`, `availability.exception.add`, `availability.request.send`, `availability.request.respond`, `availability.query` with the inputs, outputs and permissions in <issue id="1c8c53a0-396b-43a7-8fb9-c138dbbc70b2" label="EVE-67" href="https://linear.app/resnovas/issue/EVE-67/f2-scheduling-and-rosters-crew-availability-shifts-offers-call-sheets" /> section 4.
3. `availability.query` ranks people by role match, qualifications, availability kind (free over tentative), travel distance from home base when known, and returns a reason list per person.
4. Privacy: exception reasons visible only to the person and admins; schedulers see free, busy or tentative.
5. Offline: a person's own availability and the scheduler's in-scope people sync to SQLite (<issue id="60101c56-d4e4-4e4f-b7c8-b4c40f44ada0" label="EVE-17" href="https://linear.app/resnovas/issue/EVE-17/s4-choose-the-offline-sync-engine-for-record-edits-and-live-text-and" /> engine); overlapping offline edits are both kept and flagged.
6. Screens: Availability calendar and Availability request composer with projections (<issue id="91297309-acc4-4bb9-ad68-33fbc2720e5a" label="EVE-50" href="https://linear.app/resnovas/issue/EVE-50/p111-build-screen-awareness-app-state-navigation-and-the-screen" />).

## Acceptance criteria

* Weekly pattern plus an exception across a DST change returns correct free ranges in two timezones (`@effect/vitest` property test).
* `availability.query` for "rigger, 14th, 09:00 to 18:00" returns the same ranked list through the UI, HTTP and MCP surfaces.
* A scheduler cannot read an exception reason; an admin can (negative test).
* An availability request sent to 3 people records each per-range answer; the agent must confirm before sending.

## Constraints

Effect-TS v3 (Effect services, `Data.TaggedError`, Schema, `@effect/vitest`); pure availability helpers stay plain TypeScript; behind flag `f2-scheduling`; no new dependency without Jonathan approving it on this issue; WCAG 2.2 AA; whitelabel ASCII copy; ships to main per the AGENTS.md delivery exception with `node --run check` results pasted here.
