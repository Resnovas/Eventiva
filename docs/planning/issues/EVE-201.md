## Linear description

## Goal

Each department draws its plan of a space (where fixtures, truss, speakers, risers, screens and cable runs go) on top of the site map, together with others and the agent, and exchanges it with CAD and previsualisation tools.

## Context

* Parent: [EVE-73](<https://linear.app/resnovas/issue/EVE-73/f1-events-and-production-planning-the-event-record-run-of-show>) sections 4, 5 (ProductionPlan, DesignElement), 6 (Plan canvas), 8 (`SceneExchange`), decision D4 (GDTF and MVR).
* The base layer is F10's SiteMap (<issue id="f8432c08-24bb-4690-a3e1-16ed79977eee" label="EVE-108" href="https://linear.app/resnovas/issue/EVE-108/f10-interactive-site-maps" />), referenced by its UUIDv7 map id; `Space.site_map_zone_ref` stores an F10 Zone feature id. Positions use the F10 site-local frame: origin at the site anchor, x east and y north in metres, with WGS84 conversion from F10's shared contracts (<issue id="9b8adbfb-05a9-4f10-9c60-baa5bfcfd4fa" label="EVE-146" href="https://linear.app/resnovas/issue/EVE-146/f101-sites-levels-base-layers-and-calibration" />). F1 owns DesignElements and registers them as an `external` layer source through `sitemap.layerSource.register` (<issue id="82fab111-6d01-4616-85c7-1e4ff88ca469" label="EVE-152" href="https://linear.app/resnovas/issue/EVE-152/f102-site-maps-and-layers-as-yjs-documents-with-a-feature-record" />) so F10 renders them read only.
* Canvas data is a Yjs document per plan ([EVE-51](<https://linear.app/resnovas/issue/EVE-51/p112-build-collaboration-yjs-for-text-and-canvas-with-record-sync-and>)). DesignElement rows are the queryable record of what is drawn; the canvas holds geometry and annotations; the two are kept in step by one service, never written separately.

## Scope

1. Tables `production_plan` (event_id, space_id, layer kind: lighting, rigging, sound, staging, video, power, general; base map ref; canvas doc id) and `design_element` (kind, fixture_type_id, catalogue_ref to F6, position x y z in metres, rotation, unit number, weight_kg, power_w, department_id).
2. A `PlanService` that applies element actions to both the row and the canvas in one Effect, and rebuilds rows from the canvas on load if they diverge.
3. Actions: `plan.create`, `plan.update`, `element.place`, `element.update`, `element.remove`, `plan.importMvr`, `plan.exportMvr`.
4. `SceneExchange` port: MVR import creates elements and fixture types; MVR export writes positions, fixture types and patch (from F1.7). Parsing and writing MVR (zip plus XML) needs a dependency approved by Jonathan on this issue first; propose the smallest maintained zip and XML libraries with licence and size.
5. Layers from all departments can be shown together read only; edit only your department's layer unless you are production manager or above.
6. Screen: Plan canvas (map base, element palette from fixture types and F6 catalogue, inspector, layer toggles, warnings) with projection listing visible elements and selection, and every tool bound to an action.

## Acceptance criteria

* Two people and the agent place elements on the same plan, one offline; after sync the canvas and the rows agree and nothing is lost.
* The agent places "12 spots evenly along the front truss" through `element.place` and the projection shows them selected.
* An MVR file exported from a CAD tool imports with correct positions within 1 cm; exporting and re-importing is lossless for the fields above.
* A sound head cannot move a lighting element.
* Screen passes the unbound-control check and axe for the non-canvas controls; canvas tools are keyboard reachable.

## Constraints
