## Linear description

## Goal

An organisation creates record types Eventiva does not ship (for example "Artist rider", "Wristband batch", "Sponsor deliverable"), links them to existing records such as an F1 Event, and works with them like any built-in record, including through the agent.

## Context

* Parent: <issue id="d6f1d3a2-12a8-474b-abae-aa29b394d45d" label="EVE-111" href="https://linear.app/resnovas/issue/EVE-111/f14-website-builder-and-in-app-customisation" /> sections 4 (`studio.entities.*`, `records.custom.*`) and 5 (EntityTypeDefinition, CustomRecord).
* Builds on F14.1 (<issue id="4b0d8581-8ced-45cc-8540-22859dfdfe65" label="EVE-133" href="https://linear.app/resnovas/issue/EVE-133/f141-custom-fields-on-any-entity-in-the-action-inventory" />): a custom record type is a set of FieldDefinitions plus a type definition; values use the same compiled schema.
* Odoo lesson (docs/learnings/odoo-extensions-reference.md): never create a parallel model for an existing concept. The designer warns when a new type looks like an existing one (for example a "Contacts 2" type) and offers custom fields on the existing entity instead.

## Scope

1. `EntityTypeDefinition` and one generic `custom_record` table (org_id, entity_type, values JSONB / JSON text, parent_type, parent_id, owner, audit fields).
2. Generic actions `records.custom.create`, `.update`, `.delete`, `.get`, `.list` with input schema compiled per type and tenant; list supports filter, sort and pagination over indexed fields.
3. Per-type grants `records:{type}:read` and `records:{type}:write` registered with <issue id="7f612e80-3332-4acf-a74c-d35db06fe4e8" label="EVE-43" href="https://linear.app/resnovas/issue/EVE-43/p14-build-identity-and-access-orgs-authorization-user-profiles-and" /> at publish; ownership scope (org, team, event) applied by the tenant guard.
4. References: a custom type can reference any entity (F1 Event, F4 contact, another custom type); references are tenant-checked and appear as related lists on the target's screen through a view slot (F14.3).
5. Domain events `records.custom.created/updated/deleted` on the change feed (<issue id="ee08644c-eb3c-4a46-aea7-745864ad4263" label="EVE-45" href="https://linear.app/resnovas/issue/EVE-45/p16-build-the-change-flow-domain-events-and-a-durable-resource-change" />) so automations, sync and the agent see them.
6. Similarity warning in the designer (name and field overlap with existing entities).
7. Offline: records sync like built-in records; field conflicts per F14.1.

## Acceptance criteria

* Define "Artist rider" with a reference to Event, publish, create three riders from Android offline, sync, and see them on web under the Event.
* The agent lists riders for an Event and updates one through the generic actions; a user without `records:artist_rider:write` is refused on UI, HTTP and MCP (test).
* Tenant B cannot read tenant A's type definition or records (negative test on every surface).
* Archiving a type hides it and its screens; records stay until a `always`-approved purge.

## Constraints

Effect-TS v3 house rules; no zod; behind `f14-studio`; no per-tenant DDL; WCAG 2.2 AA; no new dependency without approval here; ships to main per the AGENTS.md delivery exception with `node --run check` results pasted here.
