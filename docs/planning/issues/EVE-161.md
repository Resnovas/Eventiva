## Goal

An organiser sees whether a venue room, vendor or professional is likely free on the event dates before sending an enquiry, without the vendor exposing their private calendar.

## Context

* <issue id="b22fbb0d-100b-47a3-8c32-eeacadc4c9fe" label="EVE-66" href="https://linear.app/resnovas/issue/EVE-66/f5-directory-and-marketplace-vendor-venue-and-professional-listings" /> section 4 (`directory.availability.check`) and section 7 (agent sourcing filters by date).
* Bookings, availability and rosters come from <issue id="97915f03-fb56-4efc-bb5a-15e8b62b96b2" label="EVE-33" href="https://linear.app/resnovas/issue/EVE-33/port-scheduling-primitives-for-availability-bookings-and-rosters" /> primitives; F2 rosters feed crew availability for vendors who staff jobs; F6 stock feeds equipment availability where a vendor opts in.
* Only a coarse signal crosses the tenant boundary: available, tentative, unavailable, unknown. No event names, customers or times.

## Scope

1. `directory.availability.check` (public read): listingId, date range, optional venueRoomId; returns one signal per day.
2. A vendor setting per listing: availability source (none, manual blackout dates, <issue id="97915f03-fb56-4efc-bb5a-15e8b62b96b2" label="EVE-33" href="https://linear.app/resnovas/issue/EVE-33/port-scheduling-primitives-for-availability-bookings-and-rosters" /> calendar), and whether tentative holds show as tentative or available.
3. Manual blackout dates action `directory.availability.setBlackouts` (listing:write).
4. A read model refreshed from the <issue id="ee08644c-eb3c-4a46-aea7-745864ad4263" label="EVE-45" href="https://linear.app/resnovas/issue/EVE-45/p16-build-the-change-flow-domain-events-and-a-durable-resource-change" /> change feed so public checks never query the vendor tenant's private tables directly.
5. Search filter integration with F5.4 (date range filter uses the read model; unknown never excludes a listing).
6. Availability strip component on listing detail and in shortlist comparison.
7. Offline: cached signals carry their timestamp and are shown as possibly out of date.

## Acceptance criteria

* The public signal never reveals a booking's title, customer, or time of day (schema test on the output type).
* A booking created in the vendor tenant changes the signal within one change-feed cycle (integration test).
* Unknown stays unknown when the vendor chose no source.

## Constraints

Effect-TS v3; flag `directory-marketplace`; no new dependency without Jonathan approving it on this issue; ships to main with `node --run check` results pasted here.

## Done signal

Merged with tests green, and the privacy rule written into the ai-docs.
