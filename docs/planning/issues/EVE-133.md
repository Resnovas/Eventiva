## Linear description

## Goal

An organisation adds its own fields to any extensible record (for example an F1 Event or a crew booking), and those fields are read, written, filtered, synced offline and available to the agent exactly like built-in fields, for that tenant only.

## Context

* Parent: <issue id="d6f1d3a2-12a8-474b-abae-aa29b394d45d" label="EVE-111" href="https://linear.app/resnovas/issue/EVE-111/f14-website-builder-and-in-app-customisation" /> (F14), sections 4 (Studio actions), 5 (FieldDefinition) and decision D3 (one `custom` JSONB column).
* Upstream reference at 6b5cf68: `app-config/`, `settings/` (schema-declared settings) and `data-programs/` (agent-authored data definitions), read for behaviour only.
* <issue id="dc89a6af-338c-417b-a352-80cbfb05ec1e" label="EVE-40" href="https://linear.app/resnovas/issue/EVE-40/p11-build-the-action-contract-and-inventory-in-effect-schema" /> builds a static inventory. Custom fields need the inventory to be augmented per tenant at runtime: the entity's write actions (for example F1 `events.update`) accept a `custom` object whose Effect Schema is compiled from the tenant's published FieldDefinitions, and the provider-safe JSON Schema the agent sees is generated per tenant.
* <issue id="62f3bba8-9275-4ff1-98bf-62b95f432b37" label="EVE-32" href="https://linear.app/resnovas/issue/EVE-32/port-settings-profiles-navigation-command-menu-and-onboarding" /> generates settings screens from Effect Schema; the same generator renders custom fields on forms.

## Scope

1. `FieldDefinition` table and Effect Schema; field types: text, rich text (Yjs doc via <issue id="a1348819-43cc-4005-8e8d-a896a761af03" label="EVE-51" href="https://linear.app/resnovas/issue/EVE-51/p112-build-collaboration-yjs-for-text-and-canvas-with-record-sync-and" />), number, money (amount plus currency), date, datetime, duration, boolean, select, multi-select, reference (any entity type, tenant-scoped), person, file (<issue id="8d8d301b-d679-4dac-95bb-c24889179cd0" label="EVE-25" href="https://linear.app/resnovas/issue/EVE-25/port-files-private-attachments-artifacts-and-document-import" /> handle), location, computed (declarative expression over the same record), AI (value filled by an automation step, F14.6).
2. Extensible tables declare themselves with a `custom` column helper in the shared schema package (<issue id="c31b6b08-1532-4a7a-945f-24a70bbab765" label="EVE-23" href="https://linear.app/resnovas/issue/EVE-23/split-core-into-portable-contracts-and-backend-runtime-with-a-shared" /> / D6): JSONB on Postgres, JSON text on SQLite. `indexed: true` creates an expression index through a generated migration owned by the platform, not by the tenant.
3. A `CustomSchemaRegistry` service (`Context.Tag`) that compiles a tenant's published definitions to Effect Schema, caches per CustomisationVersion, and augments entity actions' input and output.
4. Per-tenant JSON Schema for MCP, HTTP and AI tools; the parity check (<issue id="dc89a6af-338c-417b-a352-80cbfb05ec1e" label="EVE-40" href="https://linear.app/resnovas/issue/EVE-40/p11-build-the-action-contract-and-inventory-in-effect-schema" /> target) covers augmented actions with a fixture tenant.
5. Actions `studio.describe`, `studio.fields.define`, `.update`, `.archive`, `.purge` (drafts land in a change set; until F14.4 lands, a minimal publish that applies immediately behind the flag).
6. Field-level permission: inherit the entity rule; optional stricter read/write grant; `pii` fields masked in lists, telemetry and agent context without the pii grant (<issue id="7f612e80-3332-4acf-a74c-d35db06fe4e8" label="EVE-43" href="https://linear.app/resnovas/issue/EVE-43/p14-build-identity-and-access-orgs-authorization-user-profiles-and" />).
7. Offline: definitions sync as read-only data; values sync per key with last writer wins; rich text values merge by CRDT.
8. Field screens in the Field designer (section 6), and custom fields rendered on the generated form section of every extensible screen with screen-context projection entries.

## Acceptance criteria

* Tenant A adds `wristband_colour` (select) to F1 Event; the agent reads and sets it through `events.update`; tenant B's JSON Schema for the same action has no such field (test).
* Writing an invalid option fails with a typed `CustomFieldInvalid` error on every surface (UI, HTTP, MCP).
* Two devices edit different custom keys offline on the same record and both survive reconnect; the same key resolves by last writer wins (test).
* A pii field is masked for a viewer without the grant in UI, agent context and spans (test).
* Archiving hides the field and keeps values; purge deletes values and leaves an audit record.
* The parity target passes with augmented actions.
