## Linear description

## Goal

A rigger sees every hanging point, what hangs on it and whether it is within its rated load, and a named competent person signs the plan off; any later change voids the sign-off.

## Context

* Parent: [EVE-73](<https://linear.app/resnovas/issue/EVE-73/f1-events-and-production-planning-the-event-record-run-of-show>) sections 4, 5 (RiggingPoint, LoadAssignment, RiggingSignOff), 7 (human-only sign-off), 11 (LOLER, PUWER, BS 7906, ANSI E1.6), decision D5.
* Eventiva shows indicative sums only and never certifies. The competent-person qualification comes from F13 once it exists (agreed with the F13 thread); until then it is an org-level grant `f1:rigging:certify` given to named people. Once F13 ships, `rigging.signOff` also calls F13's `hr.qualifications.holds` (<issue id="9f305527-7de1-436f-89bd-27341f70624e" label="EVE-154" href="https://linear.app/resnovas/issue/EVE-154/f135-build-qualifications-requirements-and-the-eligibility-check" />) with the signer's F4 party ref, type key `rigging-competent-person` and the signing date, and refuses unless `holds` is true; the returned qualificationId is stored on the sign-off.

## Scope

1. Tables `rigging_point` (plan_id, label, position, rated working load limit in kg, structure ref), `load_assignment` (point, element or manual load, weight_kg, dynamic factor default 1.0), `rigging_sign_off` (plan_id, load summary hash, signed_by, statement text, signed_at, void flag).
2. Pure load summary function: per point total static and factored load, utilisation percent, overloads; summary hash over all points and loads. Element weights default from FixtureType or F6 catalogue and can be overridden.
3. Actions: `rigging.addPoint`, `rigging.updatePoint`, `rigging.assignLoad`, `rigging.removeLoad`, `rigging.summarise`, `rigging.signOff`. `rigging.signOff` has approval `always`, the actor must be a person (agents refused with a typed error) holding `f1:rigging:certify`, and the statement text is shown and stored verbatim.
4. Void rule: any change to points or loads after a sign-off marks it void on the device that sees the hash mismatch, and the void syncs. A voided sign-off is kept for audit.
5. Exports: a load schedule PDF and CSV that state the figures are indicative and that a competent person must verify them.
6. Agent: summarises, flags overloads and voided sign-offs, drafts the statement; cannot sign.
7. Screen: Rigging (points table, load bar per point coloured and labelled by utilisation so colour is never the only signal, sign-off panel) with projection and bound controls.

## Acceptance criteria

* Load summary tests: single point, shared truss loads entered as manual loads per point, dynamic factor, overload at 101 percent.
* The agent calling `rigging.signOff` fails with a typed error and an audit entry.
* A person without `f1:rigging:certify` cannot sign; a person with it can, and the sign-off records the hash.
* Changing one load offline voids the sign-off after sync on both devices.
* Exports carry the indicative-figures statement.
* Screen passes the unbound-control check and axe.

## Constraints

Effect-TS v3 house rules (load maths is pure TypeScript); every operation is an inventory action with one permission check, audit and change record; UI from Rambo-UI, WCAG 2.2 AA; behind PostHog flag `f1-production-plans`; no structural engineering beyond point sums; no new dependency without Jonathan approving it on this issue; whitelabel ASCII copy; people docs and ai-docs in the same commit; ships to main with `node --run check` results here.
