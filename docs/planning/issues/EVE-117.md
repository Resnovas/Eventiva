## Goal

Every paid ticket line becomes a ticket with a code that any registered device can verify offline, delivered to the holder in-app, by email and as a PDF, and voided the moment it is refunded.

## Context

* Parent [EVE-76](<https://linear.app/resnovas/issue/EVE-76/f8-ticketing-ticket-types-capacity-issuance-admissions-and-scanning>) sections 4, 5 and decisions D2 and D5.
* Code format: a compact payload (ticket id, ticket type id, event id, admission scope id, payload version, issued at) signed with a per-event Ed25519 key held in the secrets service ([EVE-41](<https://linear.app/resnovas/issue/EVE-41/p12-build-app-config-settings-secrets-and-credentials>)); the device holds only public keys. The random 128-bit secret is kept server-side to allow revocation lists.

## Scope

1. Ticket schema and status machine (valid, void, transferred-out).
2. Actions: ticketing.ticket.issueForOrder (system, called by F9 commit; idempotent per order line), issueComp (always approval for agents), get, list, search (masked by role), updateHolder, void, reissue, deliver.
3. Per-event signing keys: create on first issue, rotate on demand, publish public keys to devices; key material never leaves the secrets service.
4. Delivery: in-app ticket card with QR, email through <issue id="9aae6a50-4a43-4327-ae6a-51d18bc69b35" label="EVE-24" href="https://linear.app/resnovas/issue/EVE-24/port-notifications-messaging-channels-and-transactional-email" /> with the QR and a PDF from <issue id="8d8d301b-d679-4dac-95bb-c24889179cd0" label="EVE-25" href="https://linear.app/resnovas/issue/EVE-25/port-files-private-attachments-artifacts-and-document-import" />. QR rendering and PDF libraries are new dependencies: propose them here for approval first.
5. F9 refund or cancel calls void for that line only; voids publish to the change feed so devices learn of them on next sync.
6. Attendee list and Ticket detail screens with projections; gate-staff role masking (name and type only).

## Acceptance criteria

* Paying an F9 order with three ticket lines issues three tickets once even if the paid event is delivered twice.
* A signature check in a test using only the public key accepts a real ticket and rejects one with a changed byte.
* Refunding one line voids exactly that ticket; scan of it after sync is rejected with reason void.
* Gate staff calling ticket.get via HTTP and MCP sees no email, answers or order id.
* Email and PDF render in the test harness with the code readable by a decoder.

## Constraints

Effect-TS v3 house rules; no key material in logs, telemetry or action payloads; behind flag `ticketing`; QR and PDF libraries need Jonathan's approval here; whitelabel ASCII email copy; ships to main per the AGENTS.md delivery exception with `node --run check` results pasted here.
