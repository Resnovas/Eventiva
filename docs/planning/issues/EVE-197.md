## Linear description

## Goal

A user describes what they need in plain language and the agent drafts the fields, record types, views and automations as a change set they can review and publish; and organisations can add AI fields whose values the agent fills in under a budget.

## Context

* Parent: <issue id="d6f1d3a2-12a8-474b-abae-aa29b394d45d" label="EVE-111" href="https://linear.app/resnovas/issue/EVE-111/f14-website-builder-and-in-app-customisation" /> sections 4 (`studio.propose`), 7 (agent behaviour) and 12 (the wristband acceptance case).
* The agent already has every Studio action as a tool (<issue id="3deaef52-8db8-490c-8143-b293ab5656a8" label="EVE-52" href="https://linear.app/resnovas/issue/EVE-52/p18a-build-the-agent-turn-loop-with-actions-as-tools" />); this slice adds planning, explanation and safety so the result is reviewable, not a stream of tool calls.
* Odoo has AI fields (Odoo 19 documentation); here an AI field is a FieldDefinition of type AI whose value an automation agent step computes.

## Scope

1. `studio.propose`: input request plus scope (entity types the user is looking at, taken from the screen projection); output a draft change set with a rationale per item, reuse of existing fields where they fit (the agent must call `studio.describe` first), and the preview report. Never publishes.
2. Explain: `studio.describe` output rich enough for "why does this field exist, who added it, what uses it" (definitions, change set history, automations and views that reference it).
3. Debug: given an automation run id, the agent reads the run log and proposes a fix as a draft change set.
4. AI fields: type AI with prompt template over the record's fields, model selection through <issue id="5f3d064c-7dfa-45f3-b0a2-67d5ad9d3aca" label="EVE-53" href="https://linear.app/resnovas/issue/EVE-53/p18b-build-model-engines-model-selection-and-user-owned-subscriptions" /> (the org's or user's engine; never a silent Eventiva-funded fallback), trigger (on change of named fields, or manual), per-field monthly budget, output schema (text, select, number), stored with `ai_generated` provenance and the prompt version.
5. Evaluation fixtures: ten plain-language requests with expected change set shapes, run through the <issue id="bef04957-8bec-479e-85ee-5880dfc9fc8c" label="EVE-29" href="https://linear.app/resnovas/issue/EVE-29/port-agent-evaluations-linked-to-posthog-datasets" /> eval harness when it exists, otherwise as `@effect/vitest` tests with a recorded model.
6. Telemetry: proposal accepted, edited or discarded share; AI field cost per org.

## Acceptance criteria

* "Track wristband colour per ticket type and alert me when a type has none" yields a draft with one select field and one automation; nothing is live until a human publishes (test with a recorded model).
* When a suitable field already exists the proposal reuses it instead of adding a duplicate (fixture).
* An AI field "summary of crew notes" fills on change, stops at its budget with a visible state, and shows its provenance on the record.
* With no engine configured the AI field shows "not configured" and makes no call.

## Constraints

Effect-TS v3; Effect AI only (<issue id="07c58289-6f1c-488e-a130-5f718b473fce" label="EVE-14" href="https://linear.app/resnovas/issue/EVE-14/s1-prove-one-effect-action-serves-ui-mcp-and-ai-sdk-from-one-inventory" /> decision); behind `f14-studio` and a sub-flag `f14-studio-ai-fields`; prompts and record contents are not sent to telemetry by default; no new dependency without approval here; ships to main per the AGENTS.md delivery exception with `node --run check` results pasted here.
