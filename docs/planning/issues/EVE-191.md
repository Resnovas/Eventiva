## Linear description

## Goal

An organisation automates workflows across the whole product ("when a ticket order is refunded, notify the box office and reopen the seat") without code, using the one rules engine F3 builds, so there is a single rule builder, a single run log and a single permission model.

## Scope

1. Registration contract for feature sets: a short guide and helper so each set registers its triggers and rule-safe actions with the `rules` package (F1, F4, F6, F8, F9 and the rest as they land); a protected action can never be marked rule-safe, enforced by a check that fails registration.
2. F14 triggers: custom field changed (F14.1), custom record created, updated, deleted (F14.2), form submitted (F14.9), site published (F14.10), schedule (cron with time zone), inbound webhook (tokenised URL, signature check, 64 KB cap); F14 rule-safe actions: `records.custom.create`, `records.custom.update`, custom field set on any extensible entity.
3. Engine extensions proposed back to the `rules` package, built here with the F3 owner's agreement: wait steps (duration or until a date field), approval steps (pause until a named role approves, reusing the action approval path), branch on condition, agent step (prompt plus an allowed-actions list, budgeted, used by F14.6 AI fields), `rule.runNow` and `rule.runs.cancel`.
4. Rule scope and permission: rules on non-task triggers need `studio:automate`; task rules keep `tasks:rules` per <issue id="cbcfb707-a7d4-4089-8e84-d9e2a2bd4d94" label="EVE-235" href="https://linear.app/resnovas/issue/EVE-235/f310-build-the-task-rule-builder-when-x-then-y-on-a-generic-rule" />.
5. Change sets: rules can be drafted inside a Studio change set (F14.4) and are enabled when it publishes; rollback disables rules added after the target version.
6. Rule editor: extend the <issue id="cbcfb707-a7d4-4089-8e84-d9e2a2bd4d94" label="EVE-235" href="https://linear.app/resnovas/issue/EVE-235/f310-build-the-task-rule-builder-when-x-then-y-on-a-generic-rule" /> screen with a trigger picker grouped by feature set and the new step kinds; projections and action bindings per <issue id="91297309-acc4-4bb9-ad68-33fbc2720e5a" label="EVE-50" href="https://linear.app/resnovas/issue/EVE-50/p111-build-screen-awareness-app-state-navigation-and-the-screen" />.

## Acceptance criteria

* "Ticket order refunded then notify box office" built on F8 and F14 registrations fires once per refund, survives a runner restart mid-run and does not double-notify (<issue id="37a1be99-529e-478c-a187-48c120672aeb" label="EVE-18" href="https://linear.app/resnovas/issue/EVE-18/s5-verify-sharding-across-two-independent-runners-with-drain-and" /> two-runner setup).
* Registering `show.arm` as rule-safe fails the registration check (test).
* A rule with an approval step pauses until an organiser approves, then completes; a cancelled run stops at the next step.
* A rule drafted in a change set does nothing until the change set publishes and is disabled again by rollback.
* There is exactly one rules package and one run log in the codebase (dependency check).
