## Linear description

## Goal

A register takes card-present payments on supported readers, including store-and-forward offline payments within the organiser's limits, and prints receipts and opens a cash drawer, on phone, tablet, desktop and web.

## Context

* Parent <issue id="7d939472-20ba-4512-b231-c0f04c05574c" label="EVE-107" href="https://linear.app/resnovas/issue/EVE-107/f9-online-and-in-person-sales-storefront-point-of-sale-orders-payments" /> sections 3, 8 and decision D3. Market check (2026-11-01, provider docs): offline store-and-forward is supported on Bluetooth readers and smart readers through the iOS, Android and React Native SDKs; Tap to Pay on Android has no offline mode; Tap to Pay on iPhone offline is in private preview; EEA offline payments need chip and PIN. Competitors set per-device daily and per-order limits and advise reconnecting within 24 hours.
* The native SDK needs an Expo development build, not Expo Go (<issue id="a7a66a5c-e747-4245-bc84-3232ef65a16c" label="EVE-16" href="https://linear.app/resnovas/issue/EVE-16/s3-prove-runtime-loading-and-switching-of-a-remote-module-on-expo-web" /> records the build model).

## Scope

1. First step, before code: verify against current provider docs which reader types each Eventiva platform (iOS, Android, web, desktop) can drive online and offline, and whether desktop and web can drive smart readers over the internet. Record the matrix here. Code only what the matrix supports.
2. `CardTerminal` Effect service in the payments integration package: discoverReaders, connect, disconnect, collectPayment, cancel, offline status, forwarding events. Fake terminal Layer for tests.
3. Actions: [sales.reader.discover](<http://sales.reader.discover>), connect, disconnect; payment method `card present` in sales.payment.create.
4. Offline: enforce per-device daily and per-order limits from the channel before collecting; store-and-forward handled by the provider SDK; Eventiva records the payment as `offline stored`, then `offline forwarded` or `declined after forward` from SDK events and webhooks; a decline creates an agent suggestion and an organiser task to contact the customer.
5. Onboarding notice and setting acknowledgement that the tenant bears offline declines (D3).
6. Peripherals: `ReceiptPrinter` (ESC/POS over network and Bluetooth), `CashDrawer` (via printer kick), barcode scanner as keyboard input; sales.receipt.print.
7. Reader state, offline queue and limit headroom in the register projection.

## Acceptance criteria

* Platform and reader matrix recorded here with doc links and dates before implementation.
* Fake terminal tests: online payment, offline payment within limits, offline payment over limit rejected, forwarded success, forwarded decline creating a task.
* Real reader test (once D2 and the dependency are approved) on one Bluetooth reader with an Android development build, online and in airplane mode, recorded here.
* Receipt printed on one ESC/POS printer; drawer opens on cash sale.

## Constraints

Effect-TS v3 house rules; vendor SDK only in the integration package with `// effect-boundary:` comments; the `f9-pos-offline-card` flag defaults off; no card data in Eventiva; no new dependency, hardware purchase or vendor account without Jonathan approving it on this issue; ships to main per the AGENTS.md delivery exception with `node --run check` results pasted here.
