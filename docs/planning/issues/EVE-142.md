## Linear description

## Goal

The agent can staff an event on request: it proposes a full roster that respects every rule, explains its choices, and a person applies what they agree with.

## Context

* Slice 11 of F2 (<issue id="1c8c53a0-396b-43a7-8fb9-c138dbbc70b2" label="EVE-67" href="https://linear.app/resnovas/issue/EVE-67/f2-scheduling-and-rosters-crew-availability-shifts-offers-call-sheets" /> section 7, decision 3 recommended a). The solver is deterministic plain TypeScript using the pure rules engine (F2.3); large scopes run as a sharded Effect Cluster entity (<issue id="a626308a-598f-41ba-accd-4004cbbd9932" label="EVE-54" href="https://linear.app/resnovas/issue/EVE-54/p18c-build-durable-agent-runs-on-effect-cluster-and-workflow" />, <issue id="37a1be99-529e-478c-a187-48c120672aeb" label="EVE-18" href="https://linear.app/resnovas/issue/EVE-18/s5-verify-sharding-across-two-independent-runners-with-drain-and" /> result) and must not block the entity's other messages (<issue id="6b15bbbd-3da3-4ccf-9d05-e64298b03556" label="EVE-35" href="https://linear.app/resnovas/issue/EVE-35/keep-a-long-agent-run-from-blocking-its-entitys-other-messages" />).

## Scope

1. `roster.propose`: input scope (event, phases, requirements), objective weights (fill rate, fairness of hours, travel, cost tier, preferences), locked assignments; output RosterProposal with per-item reasons, unfilled items with why, and a score. Greedy construction plus local search with a time budget; same input and seed give the same output.
2. `roster.proposal.apply` (agent confirm) applies selected items as proposed assignments; offers are still a separate `offer.send`.
3. Agent skills: "staff X", "fill the gaps", "who should replace Sam", with explanations drawn from the proposal reasons.
4. Proactive behaviours behind `f2-agent-proactive`, off by default: unfilled 72 hours before call, offer chasers, Run of show change impact, missing clock-in alert.
5. Offline: `roster.propose` runs locally for small scopes (under 50 positions); larger scopes say they need connectivity.

## Acceptance criteria

* For a 20-person, 3-day fixture, the proposal fills every fillable position with zero block-rule breaches and returns identical output on rerun.
* A 500-position proposal finishes within 30 seconds on a runner and survives a runner drain without restarting from scratch (<issue id="ae557bfe-e194-4268-93e7-e68ee250a84a" label="EVE-34" href="https://linear.app/resnovas/issue/EVE-34/agent-runs-restart-from-scratch-when-their-shard-moves" /> behaviour checked).
* The agent cannot apply or send offers without the user's confirmation, and cannot confirm the roster at all.
* PostHog `roster_proposal_applied` records the share of items applied.

## Constraints

Solver stays pure plain TypeScript; orchestration in Effect; no optimisation library or other new dependency without approval here; behind flag `f2-auto-roster`; ships to main with `node --run check` results pasted here.
