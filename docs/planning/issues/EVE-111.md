## 1. Goal

An organisation can reshape Eventiva to the way it works and publish branded event, venue and vendor websites from its own live data, by hand, with AI help, or by asking the agent, without writing code or installing another app.

## 2. Users and jobs

## 5. Data model

All tables carry `org_id` (tenant guard, <issue id="e4fa521d-c5d2-4f24-ab86-ed41def53953" label="EVE-42" href="https://linear.app/resnovas/issue/EVE-42/p13-build-the-storage-layer-drizzle-on-postgres-and-sqlite-state" />) and standard audit fields. "Doc" means a Yjs document embedded in the record (<issue id="a1348819-43cc-4005-8e8d-a896a761af03" label="EVE-51" href="https://linear.app/resnovas/issue/EVE-51/p112-build-collaboration-yjs-for-text-and-canvas-with-record-sync-and" />): the record holds metadata and permissions, the doc holds collaborative content.

### Studio

* **ChangeSet**: id, title, status (draft, previewed, published, rolled back, discarded), author (person or agent run), items, baseVersion. Syncs offline: yes (drafts). Conflict: per item last writer wins; publishing is server-only and rejects a stale baseVersion.
* **CustomisationVersion**: immutable, monotonically numbered per org; the compiled set of all definitions. Read-only offline copy.
* **FieldDefinition**: entityType, key (stable, never reused), label (localised), type (text, rich text, number, money, date, datetime, duration, boolean, select, multi-select, reference to any entity, person, file, location, computed, AI), validation, default, pii flag, indexed flag, help. Values live in the target entity's `custom` column (D3). Conflict on values: per key last writer wins, like built-in scalar fields; rich text values are docs.
* **EntityTypeDefinition**: key, labels, icon, title template, ownership scope (org, team, event), fields. Records live in **CustomRecord** (entityType, values, optional parent link to any entity such as an F1 Event).
* **ViewDefinition** and **ViewPatch**: layout tree of field widgets and sections; patches reference named nodes and slots on base screens. Conflict: per definition last writer wins inside a draft.
* **Automations are Rules** in the shared, domain-agnostic `rules` package owned by F3 (<issue id="cbcfb707-a7d4-4089-8e84-d9e2a2bd4d94" label="EVE-235" href="https://linear.app/resnovas/issue/EVE-235/f310-build-the-task-rule-builder-when-x-then-y-on-a-generic-rule" />: Rule, RuleRun, RuleRunStep; triggers from the <issue id="ee08644c-eb3c-4a46-aea7-745864ad4263" label="EVE-45" href="https://linear.app/resnovas/issue/EVE-45/p16-build-the-change-flow-domain-events-and-a-durable-resource-change" /> event inventory; actions from <issue id="dc89a6af-338c-417b-a352-80cbfb05ec1e" label="EVE-40" href="https://linear.app/resnovas/issue/EVE-40/p11-build-the-action-contract-and-inventory-in-effect-schema" /> that the registering module marks rule-safe; runs as the owner with permissions checked at run time; durable on Effect Cluster). F14 does not define a second engine. F14.5 registers every other set's triggers and rule-safe actions, custom field and custom record events, schedule, webhook and form triggers, and adds wait, approval, branch and agent steps to the engine. Rules referenced by a change set are versioned with it.
* **CustomisationPackage**: exported JSON with format version and content hash.

### Sites

* **Site**: kind, name, subdomain, primaryDomainId, brandKitId ([EVE-30](<https://linear.app/resnovas/issue/EVE-30/port-data-widgets-saved-dashboards-and-brand-kits>)), locales, status, owner. Syncs offline: yes.
* **Page**: siteId, path, title, seo, parentId, binding (static, or collection: entity type plus filter plus slug field, for example every published F1 Event), plus a doc holding the block tree. Doc conflicts merge by CRDT; path uniqueness is checked at publish.
* **Block tree** (inside the doc): nodes of blockType, props (validated against the block's Effect Schema), children, bindings (a data path or a read action with its input; never a data snapshot, so it re-runs under the viewer's permissions, as in [EVE-30](<https://linear.app/resnovas/issue/EVE-30/port-data-widgets-saved-dashboards-and-brand-kits>) panels).
* **BlockType**: code, not data: a registry in a Rambo-UI site-blocks package plus Eventiva data-bound blocks (public schedule from Event, Phase and Segment where Segment.audience = public in a published RunOfShow (F1), ticket selector F8, product grid F9, directory listing F5, site map F10, form, gallery, rich text, hero, columns, embed). Federated modules can register more ([EVE-16](<https://linear.app/resnovas/issue/EVE-16/s3-prove-runtime-loading-and-switching-of-a-remote-module-on-expo-web>) manifest).
* **SiteVersion**: immutable snapshot of resolved page trees, menus, redirects and assets, content hash, publishedBy, note. Server-only.
* **SiteDomain**: hostname, verification token, DNS status, certificate status. Server-only; online only.
* **Redirect**, **Menu**, **FormDefinition** (synced), **FormSubmission** (server-only; contains personal data; retention set per form), **Template** (global or org).

### Offline rules

* Drafting offline: pages, menus, forms, field/view/automation drafts can all be edited offline and merge on reconnect.
* Online only: publish, rollback, domain operations, package import, automation enable and runs, AI generation (shows its offline limit instead of pretending, per <issue id="5c7aeec2-d49c-4028-9eca-1bc641d3618c" label="EVE-13" href="https://linear.app/resnovas/issue/EVE-13/establish-modular-core-foundations-for-database-adapters-expo-and" />), form submissions from the public.
* A device keeps the last published CustomisationVersion and renders with it offline; a newer version applies on reconnect at the next screen change, never mid-edit.

## 7. Agent behaviour

* When asked: build a site from a brief and an F1 Event; rewrite a section; translate; add a block; propose a customisation from a sentence ("we need to track wristband colour per ticket type") as a draft change set with an explanation; explain why a field exists and what uses it; debug a failed automation run from its log.
* Proactively (suggestions only, never applied): flag a published page whose bound F1 Event changed date or venue since publish; flag broken links and missing alt text before publish; suggest an index when a custom field is filtered on often; notice repeated manual edits and suggest an automation.
* Approval: the agent may draft anything; publishing a site or a change set, rollbacks, domain changes, enabling an automation, archiving fields, import and export of submissions are `confirm`; purging field data and removing a domain are `always`.
* All AI generation goes through the agent (<issue id="5c7aeec2-d49c-4028-9eca-1bc641d3618c" label="EVE-13" href="https://linear.app/resnovas/issue/EVE-13/establish-modular-core-foundations-for-database-adapters-expo-and" />: UIs never call models directly) using the user's selected engine (<issue id="5f3d064c-7dfa-45f3-b0a2-67d5ad9d3aca" label="EVE-53" href="https://linear.app/resnovas/issue/EVE-53/p18b-build-model-engines-model-selection-and-user-owned-subscriptions" />). Generated images and text are marked as AI-generated in the version record.
* AI fields: a field whose value an agent step computes (for example "summary of crew notes"), run as an automation step with its own budget; the value is stored and labelled as AI output.

## 9. Permissions and roles

Default role bundles (organisations can edit them once F14 ships): **Studio designer** (studio:read, design, automate), **Studio publisher** (adds studio:publish), **Studio admin** (adds studio:admin), **Site editor** (sites:read, edit), **Site publisher** (adds sites:publish), **Site manager** (adds manage, domains, submissions).

* Customisations never widen access: a custom field inherits its entity's read/write rule unless the designer restricts it further; pii fields are masked in lists, telemetry and agent context unless the viewer holds the entity's pii grant.
* Custom record types get their own grants (records:{type}:read/write) assigned through [EVE-43](<https://linear.app/resnovas/issue/EVE-43/p14-build-identity-and-access-orgs-authorization-user-profiles-and>).
* Automations are rules (<issue id="cbcfb707-a7d4-4089-8e84-d9e2a2bd4d94" label="EVE-235" href="https://linear.app/resnovas/issue/EVE-235/f310-build-the-task-rule-builder-when-x-then-y-on-a-generic-rule" />) and run as their owner with permissions checked at run time; if the owner loses access the rule pauses and the owner and an admin are told.
* External vendors and venues edit only their own F5 profile page and only the blocks the directory template unlocks.
* Public visitors are anonymous principals with `forms.submit` and `sites.reportAbuse` only, rate limited per IP and form.
* The agent holds exactly the invoking user's permissions.
* Protected actions cannot be customised away: F1 show safety rules (`show.arm` human only, `show.stopAll` always available, `rigging.signOff` human only) cannot be removed, hidden, relabelled to mislead, or invoked by custom views, view patches or automations. Any feature set can mark an action or control `protected`; F14 refuses view patches that touch one, and a protected action is never registered as rule-safe in the <issue id="cbcfb707-a7d4-4089-8e84-d9e2a2bd4d94" label="EVE-235" href="https://linear.app/resnovas/issue/EVE-235/f310-build-the-task-rule-builder-when-x-then-y-on-a-generic-rule" /> engine.

## 11. Compliance

* Personal data (UK GDPR / EU GDPR): form submissions and pii custom fields carry purpose, retention and deletion; export and erasure requests cover custom fields and submissions; the pii flag drives masking.
* Cookies and tracking (PECR / ePrivacy): published sites load analytics only after consent; the consent banner is a platform block that cannot be removed while analytics is on.
* Accessibility: published sites meet WCAG 2.2 AA; ticket and shop sites fall under the European Accessibility Act (in force from 2025-06-28 for ecommerce). The publish step blocks on missing alt text, heading order and contrast failures.
* Abuse: hosting tenant sites on our domains invites phishing; publish runs content checks (credential forms, known-bad links), and `sites.reportAbuse` feeds a takedown queue.
* Copyright: uploaded and AI-generated media record their source; takedown follows the same queue.
* Customisation audit: every published change set is in the audit log (<issue id="7f612e80-3332-4acf-a74c-d35db06fe4e8" label="EVE-43" href="https://linear.app/resnovas/issue/EVE-43/p14-build-identity-and-access-orgs-authorization-user-profiles-and" />) with author and approver.
