## Goal

Every bank line is matched to an invoice, bill, payout or rule, with the agent proposing the match and a person accepting it, so the books agree with the bank.

## Scope

1. `BankAccount`, `StatementLine`, `Reconciliation`, `BankRule`, `BankFeedConnection`.
2. Import parsers for CSV (column mapping saved per bank), OFX and CAMT.053; duplicate lines detected by date, amount and reference hash.
3. Matching service: exact reference, amount and date window, many-to-one (one payout to many orders), one-to-many (one payment to several invoices); ranked suggestions with a reason string the agent and screen both show.
4. Bank rules: conditions on description, amount, counterparty; result account, dimensions (F1 Event, Phase, Department) and tax code.
5. Actions: `accounting.bank.import`, `accounting.bank.match.suggest` / `accept` / `reject`, `accounting.bank.rule.*`, `accounting.payment.record`, `accounting.bank.connect` / `disconnect` (feed part behind flag), `accounting.bank.reconciliation.summary`.
6. `BankFeedPort` with a file-only adapter now; an open banking adapter proposal (two candidates compared on UK bank coverage, consent length, price, Effect-friendly API) posted here as a decision card before any sign-up.
7. Screen: bank reconciliation split view; projection includes the selected line and suggestions so the agent sees the same list.

## Acceptance criteria

* A fixture month of 300 lines from three bank formats imports with no duplicates on re-import.
* On the fixture, suggestions put the correct match first for at least 90 percent of lines; accepted matches post and update document status.
* The agent accepting a match without a standing rule waits for approval; with a rule (amount under limit, confidence over threshold) it accepts and the audit row names the rule.
* Feed credentials never appear in logs, spans or action payloads (redaction test).
