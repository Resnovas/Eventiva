## Goal

Personal and special category data about a worker (legal name, date of birth, tax or national insurance id, address, bank details, nationality, health and access needs, optional diversity data, emergency contacts) is stored encrypted, masked everywhere by default, revealed only for a recorded purpose, exportable to the worker and purged on schedule.

## Scope

1. SensitiveProfile and EmergencyContact tables with field-level encryption at rest, keys per tenant from <issue id="9d08c369-bac9-4eb7-b8a7-329b5ec9bff0" label="EVE-41" href="https://linear.app/resnovas/issue/EVE-41/p12-build-app-config-settings-secrets-and-credentials" />; special category fields (health, diversity) in a separate table with their own grant.
2. Actions `hr.sensitive.get` (fields, purpose; confirm for HR, none for self), `hr.sensitive.update` (no values echoed), `hr.emergencyContacts.set`, `hr.dataExport.subject`, `hr.retention.purge`.
3. A masking rule in the screen-context projection (<issue id="91297309-acc4-4bb9-ad68-33fbc2720e5a" label="EVE-50" href="https://linear.app/resnovas/issue/EVE-50/p111-build-screen-awareness-app-state-navigation-and-the-screen" />): sensitive fields appear as typed placeholders unless revealed; reveal expires when the screen closes; each reveal writes an audit row with purpose.
4. Sensitive values are marked secret in the action schema, so they never enter spans, PostHog events, prompts or agent memory (<issue id="a03acb76-125b-4ead-815e-10ec986d8413" label="EVE-44" href="https://linear.app/resnovas/issue/EVE-44/p15-build-telemetry-opentelemetry-spans-on-every-call-and-a-vendor" />, <issue id="e00f04b6-a68b-41ed-8aa3-263fb8721b32" label="EVE-56" href="https://linear.app/resnovas/issue/EVE-56/p18e-build-the-agent-harness-outbound-acp-agent-memory-and-context" />); a test asserts this for every field.
5. Sync rule: sensitive rows never sync to a device other than the worker's own; emergency contact name and phone sync to a site supervisor's device only for workers rostered on their F1 Event that day.
6. Retention policies per record kind (configurable, UK defaults from <issue id="253839bc-c987-416b-92ea-206c9e9e8d2e" label="EVE-80" href="https://linear.app/resnovas/issue/EVE-80/f13-human-resources-worker-records-onboarding-qualifications-and-leave" /> section 11), a durable scheduled purge run (<issue id="a626308a-598f-41ba-accd-4004cbbd9932" label="EVE-54" href="https://linear.app/resnovas/issue/EVE-54/p18c-build-durable-agent-runs-on-effect-cluster-and-workflow" />) that produces a purge report, and an always-approve gate.
7. Subject export: one file (<issue id="8d8d301b-d679-4dac-95bb-c24889179cd0" label="EVE-25" href="https://linear.app/resnovas/issue/EVE-25/port-files-private-attachments-artifacts-and-document-import" />) holding every HR record about the worker, in a readable format plus JSON.

## Acceptance criteria

* A crew coordinator, a line manager and the agent acting for either cannot read any sensitive field through UI, HTTP, MCP or ACP (negative tests per surface).
* An HR admin reveal records who, which fields, purpose and time; the reveal is gone after the screen closes.
* No sensitive value appears in captured spans, events or the agent context in a full test run (assertion over exported telemetry).
* A purge after the retention date removes the fields and files and leaves an audit row without the values.
* The worker can export all their data from `me.profile` with no HR step.

## Constraints

Effect-TS v3 house rules; no zod; no new dependency (encryption uses what <issue id="9d08c369-bac9-4eb7-b8a7-329b5ec9bff0" label="EVE-41" href="https://linear.app/resnovas/issue/EVE-41/p12-build-app-config-settings-secrets-and-credentials" /> provides) without Jonathan approving it on this issue; behind `hr-module`; ship to main per the AGENTS.md delivery exception with `node --run check` results pasted here. Compliance wording to be checked with an adviser before launch.
