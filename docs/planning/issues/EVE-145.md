## Linear description

## Goal

For each live event, control can form units (a vehicle with its crew, or a foot team) with call signs, and every unit's status is always known, including updates sent while a crew had no signal.

## Context

* Parent: [EVE-71](<https://linear.app/resnovas/issue/EVE-71>) actions `ops.unit.*`, `ops.status.define`, `ops.unit.setStatus`; entities Unit, StatusCode, StatusChange; ordering and safety paragraph in section 5; journey J4.
* Unit members are F13 Workers (<issue id="253839bc-c987-416b-92ea-206c9e9e8d2e" label="EVE-80" href="https://linear.app/resnovas/issue/EVE-80/f13-human-resources-worker-records-onboarding-qualifications-and-leave" />), optionally prefilled from F2 Shifts for the event; vehicle from F7.1. F1 Event is referenced by id.
* Each live event's dispatch board is one Effect Cluster entity keyed by event id ([EVE-54](<https://linear.app/resnovas/issue/EVE-54>)), with idempotent persisted messages ([EVE-39](<https://linear.app/resnovas/issue/EVE-39>)). This issue creates that entity; F7.7 adds incidents to it.

## Scope

1. StatusCode configuration per tenant with event override: code, label, colour, meaning (available, committed, unavailable). Default set: Available, En route, On scene, Returning, At base, Unavailable, Off duty.
2. Unit: call sign (unique per event), members, vehicle, capabilities (first aid, tow, 4x4, wheelchair), active from/to.
3. `ops.unit.setStatus(unit, code, deviceTime, commandId, location?)`: queued offline on the device, sent in order on reconnect. The DispatchBoard entity applies StatusChanges append-only; current status = latest by device time, except a controller change with server time after that device time wins.
4. Unit board component (part of the Control screen) with live updates through the change feed ([EVE-45](<https://linear.app/resnovas/issue/EVE-45>)); projection lists units, statuses, staleness (time since last update).
5. Metrics: status update delay (device to server) histogram, bounded cardinality (no unit ids as labels).

## Acceptance criteria

* Device offline: three status changes queued, then reconnect; server applies them in device order, and replaying the same commands is a no-op.
* Controller sets a unit to Unavailable while the device is offline with an older queued En route: the controller's status stands; the crew sees why.
* Runner kill during a burst of status changes (<issue id="37a1be99-529e-478c-a187-48c120672aeb" label="EVE-18" href="https://linear.app/resnovas/issue/EVE-18/s5-verify-sharding-across-two-independent-runners-with-drain-and" /> harness): no lost or duplicated changes after recovery.
* Call sign clash in one event fails with a typed error.
