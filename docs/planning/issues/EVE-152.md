## Linear description

## Goal

Each event phase gets a site map made of layers, each layer one collaborative Yjs document that people and the agent edit through the same actions, with a server-derived record per feature so links, search and checks work without opening the canvas.

## Context

* Parent <issue id="f8432c08-24bb-4690-a3e1-16ed79977eee" label="EVE-108" href="https://linear.app/resnovas/issue/EVE-108/f10-interactive-site-maps" /> sections 4, 5 and decision D-F10-2 (one Yjs document per layer). <issue id="a1348819-43cc-4005-8e8d-a896a761af03" label="EVE-51" href="https://linear.app/resnovas/issue/EVE-51/p112-build-collaboration-yjs-for-text-and-canvas-with-record-sync-and" /> provides the Yjs document service, record sync and authorization at sync.
* F1 (<issue id="fbcff205-decd-464a-b8ab-a1278e71fbe4" label="EVE-73" href="https://linear.app/resnovas/issue/EVE-73/f1-events-and-production-planning-the-event-record-run-of-show" />) links to this: `Space.site_map_zone_ref` points at a Zone feature here, and a ProductionPlan uses a SiteMap as its base map by `base map ref`. Map ids, layer ids and feature ids are therefore stable public identifiers (UUIDv7, never reused).

## Scope

1. Tables `sitemap_map`, `sitemap_layer`, `sitemap_feature` (mirror). SiteMap links to an F1 Event and optional Phase by id.
2. Layer document schema (Effect Schema, versioned `sitemap.layer.v1`): `features` map (Yjs `Map`) keyed by feature id; each feature holds kind (point, line, polygon, symbol), geometry in site-local metres (F10.1 frame), rotation, style, label, z, symbol id, linked entity ref, attributes.
3. Actions: `sitemap.map.create`, `.duplicate`, `.archive`; `sitemap.layer.add`, `.update`, `.reorder`, `.remove`, `.lock`, `.unlock`; `sitemap.feature.place`, `.placeMany`, `.update`, `.move`, `.rotate`, `.resize`, `.remove`, `.removeMany`, `.link`, `.unlink`. Each applies a Yjs transaction through the [EVE-51](<https://linear.app/resnovas/issue/EVE-51/p112-build-collaboration-yjs-for-text-and-canvas-with-record-sync-and>) service and returns the change record with undo.
4. Mirror: a change-feed ([EVE-45](<https://linear.app/resnovas/issue/EVE-45/p16-build-the-change-flow-domain-events-and-a-durable-resource-change>)) consumer derives `sitemap_feature` rows (centroid, bbox, length, area, link) after each accepted update; clients treat it as read-only.
5. Sync rules at the server: layer doc delivered only to roles in the layer audience; pushes to a locked layer rejected with `LayerLocked` and the client rolls back with a notice; vendor-plot layers accept only features contained in the vendor's plot polygon (`OutsidePlot`).
6. External layer registry: another module registers a layer source (`sitemap.layerSource.register` at module activation, removed on disposal, per <issue id="5c7aeec2-d49c-4028-9eca-1bc641d3618c" label="EVE-13" href="https://linear.app/resnovas/issue/EVE-13/establish-modular-core-foundations-for-database-adapters-expo-and" /> federation rules) with an id, a read action returning features in site-local metres, an optional change-feed or live stream subscription, a staleness rule and a style. Two modes: `external` (record-backed, for example F1 DesignElements on a ProductionPlan, <issue id="fbcff205-decd-464a-b8ab-a1278e71fbe4" label="EVE-73" href="https://linear.app/resnovas/issue/EVE-73/f1-events-and-production-planning-the-event-record-run-of-show" />) and `live` (latest value per subject from a stream, for example F7 unit positions, <issue id="81e5a26e-791e-4891-bb97-c481901f11d7" label="EVE-181" href="https://linear.app/resnovas/issue/EVE-181/f710-build-live-unit-positions-on-the-event-map-with-consent-and" />, stale after 2 minutes). F10 renders and applies audience rules; the owning module owns the data and its permissions. No F10 code changes to add a source.

## Acceptance criteria

* Two clients and the agent edit one layer concurrently, one client offline, and converge; the mirror rows match the final documents.
* A vendor receives only public layers and their own plot layer; an out-of-plot placement is rejected at sync.
* Undo of an agent move restores the previous geometry for every client.
* A locked-layer push from an offline client is rejected and rolled back.
* Ids are stable across duplicate (new ids for the copy, old ids untouched) and across revision snapshots.

## Constraints
