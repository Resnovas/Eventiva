## Goal

An organiser or department lead sets up "when this happens to a task, do that" rules without code, and the rules run reliably, under clear permissions, with an audit trail.

## Context

* Parent spec: <issue id="4e19a499-139f-4016-88c4-264d3a0f7c33" label="EVE-62" href="https://linear.app/resnovas/issue/EVE-62/f3-tasks-task-lists-assignments-dependencies-and-checklists-per-event" />, decision 7 (B: build a rule builder in F3).
* Market check: Asana rules and ClickUp automations both offer trigger, condition, action builders on tasks (<issue id="4e19a499-139f-4016-88c4-264d3a0f7c33" label="EVE-62" href="https://linear.app/resnovas/issue/EVE-62/f3-tasks-task-lists-assignments-dependencies-and-checklists-per-event" /> section 3). Eventiva differs in that a rule can only call inventory actions, so a rule can never do something a person or agent could not.
* Architecture (house `extendable-module-architecture`): the engine is domain-agnostic and lives in its own package; F3 registers task triggers and actions into it. F14 (customisation) later adds triggers and actions from other sets to the same engine rather than building a second one.

## Scope

 1. A `rules` package: Rule, RuleRun and RuleRunStep tables (tenant-scoped); triggers are any event registered in the <issue id="ee08644c-eb3c-4a46-aea7-745864ad4263" label="EVE-45" href="https://linear.app/resnovas/issue/EVE-45/p16-build-the-change-flow-domain-events-and-a-durable-resource-change" /> inventory; actions are any inventory action from <issue id="dc89a6af-338c-417b-a352-80cbfb05ec1e" label="EVE-40" href="https://linear.app/resnovas/issue/EVE-40/p11-build-the-action-contract-and-inventory-in-effect-schema" /> that the registering module marks rule-safe; conditions are a typed filter over the trigger payload (field equals, in, is empty, before or after a date, changed from or to).
 2. F3 registration: triggers `task.created`, `task.updated` (with field), `task.completed`, `task.assigned`, `task.unblocked`, `task.overdue` (from <issue id="d838fcc2-59de-47d6-a932-ab003b58cbab" label="EVE-89" href="https://linear.app/resnovas/issue/EVE-89/f36-build-task-reminders-watchers-and-notifications" /> timers), `checklist.signedOff`; rule-safe actions `task.assign`, `task.setStatus`, `task.update`, `task.create` (subtask or follow-up), `checklist.addItem`, `reminder.set`, `task.watch`, plus "notify" through <issue id="9aae6a50-4a43-4327-ae6a-51d18bc69b35" label="EVE-24" href="https://linear.app/resnovas/issue/EVE-24/port-notifications-messaging-channels-and-transactional-email" />. `task.delete`, `checklist.signOff` and `guest.inviteToTask` are never rule-safe.
 3. Actions `rule.create`, `rule.update`, `rule.enable`, `rule.disable`, `rule.delete`, `rule.list`, `rule.get`, `rule.preview` (dry run against the last 20 matching events, showing what would change), `rule.runs` (history).
 4. Permissions: a rule runs as its owner, with the owner's permissions checked at run time (<issue id="7f612e80-3332-4acf-a74c-d35db06fe4e8" label="EVE-43" href="https://linear.app/resnovas/issue/EVE-43/p14-build-identity-and-access-orgs-authorization-user-profiles-and" />); if the owner loses access, the rule pauses and the owner and a tenant admin are told. Creating rules needs `tasks:rules` on the list or Event; tenant admins can see and pause all rules.
 5. Approvals: an action with confirm or always approval inside a rule pauses that run and asks the owner; it never auto-approves.
 6. Reliability: runs execute server-side as durable jobs on Effect Cluster (<issue id="a626308a-598f-41ba-accd-4004cbbd9932" label="EVE-54" href="https://linear.app/resnovas/issue/EVE-54/p18c-build-durable-agent-runs-on-effect-cluster-and-workflow" />), at least once with an idempotency key per trigger event and rule, so a retry never applies a step twice. Loop guard: a rule's own writes carry its run id and do not re-trigger the same rule; a chain stops at depth 5 and is flagged.
 7. Offline: rules do not run on devices. A device edit triggers rules when it syncs; the device shows rule results as normal synced changes.
 8. Screens (Rambo-UI, <issue id="91297309-acc4-4bb9-ad68-33fbc2720e5a" label="EVE-50" href="https://linear.app/resnovas/issue/EVE-50/p111-build-screen-awareness-app-state-navigation-and-the-screen" /> projections, every control bound to a `rule.*` action): rule list per Event or list, rule editor (trigger, conditions, actions as rows; keyboard usable), preview panel, run history with per-step outcome.
 9. Agent: the agent can create and edit rules through the same actions (confirm on `rule.enable`), explain why a rule fired from `rule.runs`, and suggest a rule when it sees the same manual edit repeated.
10. Telemetry: events `rule created`, `rule enabled`, `rule run` (outcome, step count, duration, no task text); flag `tasks-rules`, default off.

## Extension points kept for F14 (<issue id="8a7a26ad-455f-4ef7-a0e4-4dc75882ccc6" label="EVE-191" href="https://linear.app/resnovas/issue/EVE-191/f145-automations-extend-the-f3-rules-engine-across-every-feature-set" />)

F14.5 extends this engine rather than building its own, so the `rules` package design must leave room for these without a schema rewrite. They are not built here:

* Trigger and action registration from any feature set (registry keyed by module, not hard-coded to tasks).
* Step kinds beyond action: wait, approval, branch, and a budgeted agent step. RuleRunStep stores a step kind and step state so new kinds slot in; the run is a durable workflow that can pause.
* `rule.runNow` and `rule.runs.cancel` actions.
* A registration check that refuses protected actions (for example F1 `show.arm`, `rigging.signOff`) as rule-safe; F3 implements the check with its own never-rule-safe list so F14 only adds entries.

## Acceptance criteria

* Rule "when a task in Lighting is completed, create a follow-up task assigned to the lighting lead due 1 day later" fires once per completion, including after a runner is killed mid-run.
* A rule whose owner is demoted to crew pauses on its next run and notifies the owner and an admin.
* A rule that assigns a task to its own trigger condition does not loop; a 6-deep chain stops and is flagged.
* `rule.preview` shows the changes the rule would have made on recent events and writes nothing.
* `task.delete` cannot be chosen as a rule action through UI, HTTP or MCP.
* An offline completion triggers the rule once on sync, not on the device.

## Constraints

Effect-TS v3 house rules; condition evaluation is pure TypeScript; no new dependency without Jonathan approving it on this issue; WCAG 2.2 AA; whitelabel copy; ships to main per the AGENTS.md delivery exception with `node --run check` results pasted here.
