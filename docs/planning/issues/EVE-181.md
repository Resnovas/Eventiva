## Linear description

## Goal

Control sees where every active unit is on the event's site map, the dispatch suggestions use distance, and location is collected only while a person is on an active unit, or is rostered on a live event's current F2 Shift and has opted in (for example stewards on foot), with a visible indicator and short retention. This is the single location collector in Eventiva; F10.9 (<issue id="65408e38-c1f0-4c12-bb84-250acaadf65d" label="EVE-205" href="https://linear.app/resnovas/issue/EVE-205/f109-crew-positions-layer-and-as-built-reporting" />) renders its Crew layer from this stream.

## Context

* Parent: [EVE-71](<https://linear.app/resnovas/issue/EVE-71>) actions `ops.position.report`, `ops.position.list`; entity PositionFix; section 11 compliance; decision D3 (recommended: phone GPS first, telematics port in F7.11, no adapter).
* The map, layers and zones are F10 (Site map, Layer, Zone); F7 adds a unit-positions layer and does not own map rendering or geocoding.
* Positions are a live stream through the DispatchBoard entity, not records in the offline sync engine.

## Scope

1. Device reporter: while MDT mode is on and the unit is active, or while the person is on a current Shift of a live event and has opted in (opt-in is per event, revocable at any time, off by default), report position every 15 seconds when moving, every 2 minutes when still (event settings), using the platform location API already available to Expo builds; check whether the needed Expo module is already a dependency and, if not, ask for approval on this issue before adding it.
2. `ops.position.report` validated and rate-limited per device; `ops.position.list` returns latest per unit with age and accuracy.
3. Retention: history kept 30 days by default (tenant can shorten, not extend beyond 90), then deleted by a durable job; last known only after that.
4. Consent and transparency: indicator in the app while reporting, a stop button that sets the unit status to Unavailable, and a tenant DPIA template in the docs.
5. Map layer for F10: register at module activation with `sitemap.layerSource.register` (F10.2, [EVE-152](<https://linear.app/resnovas/issue/EVE-152/f102-site-maps-and-layers-as-yjs-documents-with-a-feature-record>), scope 6), mode `live`, giving `ops.position.list` as the read action, the position stream subscription, staleness 2 minutes and a style (unit markers coloured by status, stale greyed). F10 renders and applies audience rules; F7 owns the data and consent. Positions are sent as WGS84 lon/lat; F10 shared contracts convert to the site-local frame. Crews see other units only if the event setting allows.
6. One collector: `ops.position.report` is the only place device location is collected in Eventiva, for people on active units and for opted-in crew on a current Shift; F10.9 ([EVE-205](<https://linear.app/resnovas/issue/EVE-205/f109-live-positions-and-as-built-reporting>)) crew positions read from this stream rather than collecting separately, so there is one consent path and one retention rule.
7. Feed distance into `ops.dispatch.suggestUnits` (F7.7).

## Acceptance criteria

* No position is accepted for a person who is neither on an active unit nor on a current Shift with opt-in (negative tests for each, and for opt-in revoked mid-shift).
* Positions carry a source (unit or crew) so F10 can render Unit and Crew layers separately.
* Retention job deletes history older than the setting, verified with a fixture.
* Stale positions show as stale on the map and are not used for distance ranking.
* No coordinates reach analytics or logs; spans carry only counts.

## Constraints

Effect-TS v3 house rules; no zod; Rambo-UI; behind `eventiva-live-ops`; UK GDPR / EU GDPR data minimisation; no new dependency without Jonathan approving it on this issue; tests with `@effect/vitest`; docs; ships to main per the AGENTS.md delivery exception with `node --run check` results pasted here.
