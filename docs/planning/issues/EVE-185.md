## Linear description

## Goal

Every customisation, by a person or the agent, is drafted in a change set, previewed with its full impact, published deliberately as a numbered version, and can be rolled back in one step or moved to another organisation as a package.

## Context

* Parent: <issue id="d6f1d3a2-12a8-474b-abae-aa29b394d45d" label="EVE-111" href="https://linear.app/resnovas/issue/EVE-111/f14-website-builder-and-in-app-customisation" /> sections 4 (`studio.changesets.*`, `studio.packages.*`), 5 (ChangeSet, CustomisationVersion, CustomisationPackage) and offline rules.
* F14.1 to F14.3 ship with an interim "apply immediately" publish behind the flag; this slice replaces it.
* Agent approval (section 7): publish and rollback are `confirm`; import is `confirm`.

## Scope

1. `ChangeSet` with items (field, entity type, view, patch, automation definitions) and a `baseVersion`; several open change sets per org; drafts sync offline.
2. `studio.changesets.preview`: schema diff, affected screens and actions, data effects (records touched, values that will fail new validation, index builds), permission impact (new grants, widened visibility), protected-target refusals, skipped patches.
3. `studio.changesets.publish`: server-only; validates against the current version, refuses a stale `baseVersion` with `ChangeSetStale` and offers a rebase; compiles a new immutable `CustomisationVersion`; invalidates the F14.1 schema cache; emits `studio.version.published` on the change feed; audit record with author and approver.
4. Value migrations on publish are additive only: new fields get defaults lazily; type changes that lose data are refused (archive and add a new field instead).
5. `studio.changesets.rollback`: publishes a new version equal to an earlier one; data written to fields added after it is kept but hidden.
6. Clients pick up a new version at the next screen change, never mid-edit; offline devices keep the last version.
7. `studio.packages.export` (signed JSON with format version and content hash) and `studio.packages.import` (creates a draft change set; references to missing entities are reported in preview).
8. Change set review screen with DiffViewer; comments via <issue id="b7f17f15-c893-46e9-9b3b-2aefae473802" label="EVE-27" href="https://linear.app/resnovas/issue/EVE-27/port-comments-mentions-and-review-suggestions-on-any-resource" /> when available.

## Acceptance criteria

* Two admins edit different change sets; publishing the second after the first returns `ChangeSetStale`, rebase succeeds and both changes are present (test).
* Preview of a change that makes a field required reports the count of existing records missing a value.
* Rollback restores the previous screens on web and Android while keeping data entered in the meantime.
* Export from org A and import into org B produces an equivalent draft; publishing it gives the same screens.
* The agent's `studio.changesets.publish` call asks for confirmation; without it nothing changes (test).

## Constraints

Effect-TS v3; behind `f14-studio`; publish runs as a durable workflow on Effect Cluster (<issue id="a626308a-598f-41ba-accd-4004cbbd9932" label="EVE-54" href="https://linear.app/resnovas/issue/EVE-54/p18c-build-durable-agent-runs-on-effect-cluster-and-workflow" /> pattern); no new dependency without approval here; ships to main per the AGENTS.md delivery exception with `node --run check` results pasted here.
