## External effects, outbox and reconciliation

A1 is a local authoritative transaction, not a distributed undo mechanism. `Integrity` in `invocation.ts:180-203`, [the action guide](../actions.md#supply-trusted-platform-services) and [the storage guide](../storage.md#atomic-actions-and-exact-values) require external actions to stage an outbox command, not send an irreversible provider request from the handler. This is a handler/composition obligation, not runtime network sandbox enforcement. SQL `enqueue` only inserts intent. The conformance test proves a staged outbox entry commits or rolls back with domain/history/receipt; it never sends a payment.

The existing SQL hook path has leased/fenced claims and stable idempotency keys. [The hook contract](../hooks.md) explicitly says at-least-once: an external sink can complete after losing its lease, and a crash after external success but before acknowledgement needs sink-side durable deduplication or authoritative reconciliation. SQL rollback and settlement fencing cannot reverse the external effect. This investigation does not adopt the EVE-276 lane's pending changes or certify its fencing work.

Existing SQL `Storage.reconcile` records exact payment-event ledger evidence and rejects changed duplicate events; conformance races an amount larger than safe JavaScript integers and verifies immutable original text. It neither queries nor reverses a payment provider. The separately approved marketplace [trust profile](../trust-profile.md#recovery-and-compensation) and pure `contracts/marketplace-policy.ts:153-168` require ambiguous outcomes to reconcile by stable idempotency key first, reverse completed earlier steps on bounded permanent failure, and use manual recovery once payment collection starts. These are scoped marketplace policy decisions/pure functions, not a generic action reversal implementation or executed remote compensation. No external effect was sent by this lane and no new reversal architecture is authorized or needed to describe the existing limit.
