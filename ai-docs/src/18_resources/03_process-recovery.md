# Resource transaction process-loss evidence

Use `tests/storage/fixtures/resource-process.mjs` and `tests/storage/src/resource-process.spec.ts` for EVE-258/EVE-261 gate C process-loss evidence. Read [the execution guide](../../../docs/resource-process-recovery.md) for commands, defaults, disposable database restrictions and interpretation. The executable fixture is the public-service composition example; it imports emitted package subpaths without aliases.

The composition is `resourceProvider(dialect, tenant, identity, definitions)` on one captured SQL client, `resourceRuntime(provider, syntheticPolicy)` and `durable` supplied with that exact `provider.storage` plus matching `CurrentTenant`. Supply matching `Caller`/`CurrentTenant` per resource operation. Open the outer boundary through `Resources.transaction`, nest `Integrity.commit`, and create the record plus synthetic command outbox entry through the existing public services. Do not replace the provider's transaction owner with independently built Storage, another client or raw SQL.

In the default `proof` mode, apply numbered Storage migrations and `migrateResources` to completion before launching crash workers. `migrateResources` owns its transaction and rejects ambient transactions. The retained schema is a control, not a migration-crash result.

The first worker pauses after nested create/Integrity have produced provisional record, immutable revision, outbox, completed commit result and receipt, but before the outer resource transaction returns. The coordinator verifies isolation, sends SIGKILL and verifies all five sets are empty; the next process reopens and sees empty public record/history. The second worker commits the same request and pauses before IPC acknowledgement. After SIGKILL, a third process reopens, returns the exact stored result/receipt on the same Integrity key with `replayed: true`, and runs no execute effect. The five retained rows and schema remain unchanged. Update/delete probes confirm revision, receipt and completed commit immutability.

The proof asserts distinct PIDs, real `null/SIGKILL` exit events and missing operation acknowledgements. Worker barriers suspend indefinitely; no worker finalizer substitutes for a crash. The coordinator alone cleans up the disposable database/files after observation. The spec checks both dialect summaries. Run the SQLite-only command while working without PostgreSQL approval; central validation must run both dialects against the approved disposable fixture without treating the filtered case as full gate evidence.

Treat the default result as **local resource transaction process-loss proof only**. It establishes neither migration-crash safety nor producer semantics, external effects, power-loss/device durability, production policy or general exactly-once behavior. Keep its `migrationCrashProof: false`, full conformance, type, boundary and coverage gates intact.

## Separate declaration migration proof

Run `pnpm nx run @eventiva/storage-tests:migration-proof --skip-nx-cache` with the approved disposable PostgreSQL fixture from `docs/storage.md`. The uncached target builds emitted public packages and sequentially runs `resource-process.mjs migration-proof sqlite` and `migration-proof postgres`; storage `test` depends on this target. Do not edit the held parent spec or interpret the default transaction report as migration evidence. A false assertion exits nonzero before the success summary; PostgreSQL is never skipped for missing credentials/fixture.

The mode seeds two asymmetric v1 records (three revisions on one, one on the other). The child calls public `migrateResources` with complete additive v1/v2/v3 history. A fixture-local proxy delegates the real client's `withTransaction`, pausing its completed migration effect inside that transaction, with v2/v3 definitions and checksums visible only to the worker. The coordinator independently reads exact v1 schema and record/revision rows before SIGKILL and again after it. A distinct process reopens and checks the public v1 record/history; a retained old-provider write confirms usability and appends one v1 revision.

Retrying the full history applies exactly v2/v3. The second child pauses only after the actual transaction returns, before sending its operation acknowledgement. SIGKILL at this boundary leaves the committed declaration bytes/checksums and all five v1 revisions unchanged. A third process reopens the current provider and repeats the same history twice with empty migration evidence. Compare exact retained SQL rows after each repetition, not merely counts or printed booleans.

Change the original module-version pin consistently across the candidate history and verify pure preflight still returns `ready`; the real applied-prefix check must then reject it with `unsafe-migration`. A provider captured at v1 must reject a revision-correct write with `schema-mismatch` and leave all state unchanged. A freshly composed v3 provider can append revision 5 with the new optional fields, preserving every original revision and the unrelated record. Assert distinct PIDs, actual SIGKILL exits, missing acknowledgements and complete result evidence. The shared IPC deadlines remain 15 seconds per response/barrier and 10 seconds per kill; no parent timeout changes are needed.

This separate mode is **local declaration migration process-loss proof only**, not power-loss durability, distributed migration/lease fencing, native execution, production least privilege or complete G04/EVE-258/EVE-42 acceptance. No production adapter, migration policy, feature activation, dependency or secret changes are required.
